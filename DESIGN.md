# yavc.app design

yavc.app is a PUDL desktop of applications, each of which also runs on its own at `{slug}.yavc.app`. The name stands for "Yet Another Vibe-Coded", said with a straight face; the applications are developed agentically, with specifications and review, and the name is the joke. This document records the decisions taken so far and the shape they imply. The architectural principles that apply to every one of Paul's projects are in `C:\Users\paul\OneDrive\Documents\Architectural Principles.md` and are not restated here.

## Decisions

Each decision is dated and numbered so that later documents and cards can refer to it.

1. **One application, two addresses** (2026-11-02). Every application runs in a window on the desktop at `yavc.app` and as a standalone page at `{slug}.yavc.app`, from the same files and with the same data. The standalone page has no desktop chrome. A reader who wants only the RSS reader links to `rss.yavc.app` and never sees the desktop.
2. **State lives in the engine, identified by a site-wide session cookie** (2026-11-02). Because each subdomain is its own browser origin, local storage cannot be shared between the desktop and a standalone page. The engine sets an anonymous session cookie with `Domain=yavc.app` on first visit, which RFC 6265 says is sent to every subdomain, and every host page loads and saves application state through the engine. Applications never touch local storage or the address except on their own page, as the PUDL applet contract already requires; the host answers `pudl:applet-state` and listens for `pudl:applet-change`. When accounts arrive, the anonymous session becomes a signed-in one and the applications do not change.
3. **A fresh Go engine** (2026-11-02). The parkscomputing.com engine (ASP.NET, SQL Server, Docker) is not reused. The new engine is written in Go. What carries over from parkscomputing.com is the design of four things, reimplemented: the desktop shell with Classic and Windowed views, the virtual file system with a guest home and server mounts, live editing of any page in the on-site editor, and site navigation driven by an XferLang file.
4. **XferLang over JSON inside the site** (2026-11-02). Configuration, navigation and the engine's own representations are XferLang. Where another system needs JSON, the engine translates at the edge, by HTTP content negotiation (`Accept: application/json` gets JSON, the default gets Xfer). A Go XferLang library is a sub-project of the engine; see open question 1.
5. **PUDL at its current tag, copied in** (2026-11-02). The site has its own copy of PUDL `dist/` from a tagged release, 0.96.2 at the time of writing, with skins and themes switchable by the reader.
6. **No third-party scripts but Plausible, and no cookie but the session** (2026-11-02; amended 2026-11-03). PUDL ships its own fonts, so no page loads fonts or styles from another host. The only cookies are the anonymous session and, for the administrator, the sign-in session. On 2026-11-03 Paul added Plausible Analytics, whose script every page loads from plausible.io (the site layout's `<head>`). It is the one exception: it sets no cookie and keeps no personal data, so the cookie rule stands and no consent banner is needed, and the privacy page describes it. Since 2026-11-13 the script is sent only on the public site, over HTTPS (decision 147). Cloudflare, which proxies the site, can add its own Web Analytics beacon to every page on the way through. That stays turned off (2026-11-03, Paul) by a Configuration Rule on the yavc.app zone, which matches every hostname ending in `yavc.app` and turns on "Disable Real User Monitoring (RUM)". The content security policy would block the beacon if it were turned on again.
7. **Apache-2.0** (2026-11-02). The repository's own code is under the Apache License 2.0, matching PUDL, PUDL Desktop, the package format and the terminal code that parkscomputing.com relicensed for reuse. Installed packages keep their own licences beside them; Sudoku's is MIT.
8. **Package manifests stay JSON** (2026-11-02). The applet package format is shared with parkscomputing.com and PUDL Desktop, so decision 4 applies to the engine's own files and representations, not to `applet.json`.
9. **PUDL Desktop's package scanner and host-kit wiring are lifted, not rewritten** (2026-11-02). The engine as a whole is fresh (decision 3); the code that reads manifests and builds `window.pudlHost` is the same job and comes from PUDL Desktop under Apache-2.0, with its header.

10. **About is a dialog with an address** (2026-11-02). Paul asked for About yavc.app and About PUDL as modal dialogs. The architectural principles keep modals for confirmations, so this is an explicit exception, on the pattern parkscomputing.com settled for its sign-in dialogs: each dialog has an address of its own (`/about`, `/about/pudl`) that draws the page with the dialog open, and a link to it opens the dialog in place with the address following.

11. **A guest's files stay in the browser** (2026-11-02). Paul ruled that guests get no space on the server. The virtual file system's home for a reader without an account is kept in the browser's local storage, as parkscomputing.com keeps it, under the quota that site uses, and it is therefore per origin: a file saved on the desktop is not seen at a subdomain, and the other way round. Decision 2 still applies to the small state it names, an applet's continuity string and the appearance choices, which the engine keeps under the session. Applet settings are kept there too, and shown as files under `~/.config` (decision 22). A home on the server, shared by every origin, arrives with accounts, and with it the administrator's mounts.

12. **Every application's commands are an API, discoverable without the source** (2026-11-03). Paul set this as a requirement: each application publishes a manifest of its actions, the engine serves the catalogue of them and an MCP server, and because the files and the applications are in the browser (decision 11) an agent's invocation is relayed to a page the person has open and run there, as the person, with the person asked before an action does more than the agent's token allows. The design, with its own numbered decisions, is `docs/agents-design.md`.

13. **A home folder starts with stock files, kept as files on the site** (2026-11-03, Paul). A reader's home begins with `README.md`, a `Howto` folder of guides (a deck about Slides, and notes on Slides and the Editor, with screenshots served from the site), a `Documents` folder that the Save As dialogs start in, `bin` with a first script, and two sample files. They live under `site/home` in the repository, which the engine hands to the browser at `/api/site/home`; the browser seeds each file once and remembers what it seeded, so a reader who deletes a guide keeps it deleted, and a guide that changes on the site replaces the reader's copy only while that copy is still as it came. Pictures stay out of the home folder until it can hold more than text (decision 11).

14. **A home folder holds pictures, in the browser's database** (2026-11-03, Paul asked for a picture dialog that finds or uploads a picture, and for a click on a picture to edit it). The home record in local storage keeps text files as before; a picture, or any other file that is not text, is kept as bytes in the browser's IndexedDB under an id the home record points to, so the 2 MB record is not spent on it. Such a file is uploaded, downloaded, renamed, moved, copied and deleted as any other, but the Editor and the Terminal do not open it as text. A picture in a document is written as a path, `cat.png` beside the document or `~/Pictures/cat.png`, which the preview marks as an attachment and the page reads from the home folder; pictures from the site (`/static/…`) and the web load as they are. The dialog itself is the kit's (`apps/md-editor`), shared by the Editor and Slides: Insert, Picture and the `/` menu open it, with Browse for a picture already in the home folder or on the site and Upload for one from the computer, and a click on a picture in Visual view opens it on that picture to change its address, description, width and caption or to remove it. Decision 11 still holds: the pictures live in this browser, per origin, and a deck's PowerPoint and PDF exports draw them from there.

15. **A page wraps to its pane** (2026-11-03, Paul asked whether text should wrap to the widest element or to the window). The Editor's Visual view and Preview are Markdown drawn for reading, not a printed page, so text wraps to the width of the pane, with the page's own margin, and nothing in the document makes the page wider: a picture scales down to the column, and a code block or a wide table scrolls within itself. A view sized to a printed page, for documents that will be printed or exported as pages, is open question 4.

16. **Shortcodes are edited as rich text in the page view** (2026-11-03, Paul: editing them only as raw Markdown would stop people using the thing). A container shortcode is a box on the page whose body is edited as blocks, a block shortcode is a form, and a span shortcode is a mark. The design is `docs/page-view-design.md`.

17. **Properties are front matter, edited safely** (2026-11-03, Paul asked for stock and custom properties in the Editor and Slides, with safety and validity checks on the YAML). File, Properties in the Editor and Deck, Properties in Slides open one dialog, the editing kit's: the stock properties (title, author, subject, keywords, lang and date) and any others, each a name and a value, which may be added, changed and taken out. The engine reads the front matter with a real YAML parser (gopkg.in/yaml.v3, in `internal/frontmatter`) and refuses front matter that is not valid YAML, is not a mapping of names to values, or repeats a name, saying which line. A change rewrites only the lines of the properties it changes, keeping comments, blank lines, quoting and the order of the rest; a value is quoted wherever YAML would otherwise read it as something else; and the result is read back and compared with what was asked before it is written. A property written as a nested mapping, over several lines, or with an anchor, alias or tag is shown and left alone. Slides keeps its deck's front matter as written for the same reason, where it used to rebuild it on every save. The PDF export takes the subject, keywords, language and date, and the PowerPoint export the subject.

18. **Nothing goes back to parkscomputing.com for now** (2026-11-03, Paul). yavc.app took the designs it needed from parkscomputing.com (decision 3) and does not merge its work back. If the two meet again, the likelier course is to reshape parkscomputing.com around what yavc.app has become, so yavc.app keeps no compatibility with that site's engine. The package format stays shared (decision 8).

19. **Help is a set of pages with addresses** (2026-11-03, Paul). Each application's help is a page of the site, written in Markdown in the repository and served by the engine, with an address of its own that can be linked to, bookmarked and opened in a window on the desktop or as a page by itself. An application's Help menu links to its page. Files' Quick Help, a modal dialog today, becomes such a page. The guides in a reader's home folder (decision 13) overlap with this help, so the instructions move to the help pages, and the home folder keeps the deck and documents as samples to open and edit, each linking to the help page about it.

    As built, an application's help is `pages/help/{name}.md`, served at `/help/{name}`, and `/help` is the contents, whose list of applications the engine writes from the installed packages that have a help page, so it cannot fall behind them. Only an installed package's help is served, and any other address under `/help` is 404. A window's key cannot hold a slash, so the help pages' slugs are `help` and `help-{name}`; those are their window keys, their entries in the site tree under `/site/help`, and their names in the Terminal, and `/help-{name}` redirects to `/help/{name}`. At an applet's subdomain, `/help` redirects to that applet's help at the desktop's host, or to the contents when it has none, and `/help/{name}` redirects to the same address there, as every other site page does. The Files and Terminal guides moved to `/help/files` and `/help/terminal`, and their old addresses redirect. The Help menu links to the contents and to every application's help, opening a window on the desktop, and the standalone page's Help menu links to its own application's help and the contents. The links are in the layout because a row an applet adds to a shared menu is always a button in PUDL 0.96 and 0.97, so an applet's own Help item would have to navigate from script. If PUDL gains link rows for applets, each applet can link to its own help instead. The `help-pages` rule in `scripts/check.mjs` requires a help page for every package under `apps/` and checks that every link to `/help/...` leads to one.

20. **Reading keeps a session alive** (2026-11-03, Paul). A session's Seen time used to move only when something was written, so a reader who only read lost the session after the retention period, and the cookie itself was set once with that lifetime and never renewed. Now every request that carries the cookie, other than for a versioned file, records that the session was used once its Seen time is a day behind (or a quarter of the retention period, if that is shorter), and sets the cookie again with the full retention period. Reading costs at most one write to the store a day.

21. **Labels are title case** (2026-11-03, Paul). Every label in the site's own code is written in Chicago-style title case. The first and last words and every major word are capitalised, and the articles, the coordinating conjunctions and the short prepositions (a, an, the, and, but, or, for, nor, as, at, by, in, of, on, to, up, via, with, from, into and per) stay lowercase unless they come first or last. Product names, file names and paths keep their own spelling, so yavc.app, PUDL and ~/.config are written as they are, and an ellipsis stays where it was. A label is any text a person reads as a control or as the heading of a group of controls: menu titles and items, command names, toolbar buttons and their tooltips, accessible names on controls, dialog titles and dialog buttons, tab names, field labels, segmented-control options, and the menus and links in the layout. Help text, descriptions, notices, error messages, placeholders written as sentences, and the content of documents are sentences and keep sentence case, as does a dialog title phrased as a question. The packages under `applets/` are maintained elsewhere and follow their own style until they are changed there. The `title-case-labels` rule in `scripts/check.mjs` enforces this on command labels, `label:` fields and `aria-label` attributes in the site's scripts, and on the short link, button and menu text and the control attributes in the layout, with the list of minor words kept in that one place.

22. **Settings live in the session and appear as files** (2026-11-03, Paul approved the recommendation in what was open question 5). Settings had been built as files in the browser's home folder, which each address keeps separately, so key bindings chosen in the Editor on the desktop did not apply at `editor.yavc.app`. The engine now keeps every applet's settings under the reader's session, which all the addresses share, with the time each last changed, and the browser shows them as the files of `~/.config`. Physically they are in the session's file in the engine's data folder (the `yavc-data` volume in production). The folder is read in one request, at most 1 MB, when a page loads its files, and again when the page comes back into view. Writing `~/.config/<name>.json` sends it to the engine, which refuses text that is not a JSON object, a name that is not lowercase letters, digits and `-`, and anything over 64 KB for one setting or 1 MB in all. Deleting the file forgets the setting, and the folder holds no subfolders and no pictures. The applets call the settings module as before. Settings that a browser still holds from the older build move to the session the first time a page of that address loads them. When the session already has a setting of the same name, the session's text stands, and a differing local copy, or a file that cannot be a setting, is kept in `~/.config-old` so nothing goes without the reader seeing it. When accounts arrive and the home folder moves to the server, `~/.config` becomes an ordinary folder there.

23. **Production runs on a flat-rate server behind Cloudflare** (2026-11-03, Paul). The site moves off Paul's workstation to a Linode Shared CPU 2 GB server in Chicago, at $12 a month with 2 TB of transfer pooled across the account and $5 for each TB beyond. Paul wanted a host that a day on the front page of Hacker News cannot turn into a large bill, and room to grow into accounts with storage tiers. A fixed monthly price meets the first, and Cloudflare in front absorbs the static files, so the server sends little more than HTML and small API answers. Usage-billed platforms were ruled out because their bill follows the traffic. The workstation has more than enough capacity and fast fibre, but running a public service with accounts there puts it beside Paul's source and credentials, ties its uptime to the workstation's restarts, and adds a Pacific crossing to every dynamic request from the United States, where most readers are expected. Chicago keeps the delay low for both American coasts and for Europe. The server opens a Cloudflare tunnel outward and accepts SSH from Paul's address only. Releases are git tags built into images by GitHub Actions and pulled by exact tag, so a rollback is the previous tag. The workstation stays as staging. Readers' files, when accounts arrive, are to go in Cloudflare R2, which charges nothing for egress, with the engine enforcing each tier's quota and a limit on writes. `docs/deploy.md` is the procedure.

24. **Documents are the Editor's, as decks are Slides'** (2026-11-03, Paul asked for the Editor to become a Word-class editor over Markdown, with the custom styles and shortcodes Slides has). A file named `something.docs.md` opens in the Editor's Document view, drawn as pages with headers, footers and page numbers from its front matter, styled by a theme, a stylesheet of the person's and its own `{{style}}` blocks, and extended by its own shortcodes, which are macros over Markdown and can do nothing Markdown cannot. The rich editing that is not about pages goes into the page view every view shares, so Visual gains it for every Markdown file. The design, with its own numbered decisions, is `docs/docs-design.md`; it answers open question 4.

25. **Diagrams sit on D2 and Mermaid** (2026-11-03, Paul asked for a Diagrams application at `diagrams.yavc.app` with a visual editor, a text editor or both side by side, and diagrams that embed in the Editor and Slides, and left the language to the designer). A diagram is a `.d2` or `.mmd` text file with nothing beside it. D2 is the native language, edited visually and as text, because its own Go packages edit its source and report where each object is written, which was checked by building them; Mermaid is supported as text with a live preview. D2 is compiled to WebAssembly from a pinned release and runs in a worker in the browser, so a diagram's text stays there (decision 11). A document embeds a diagram with `{{diagram:path}}`, or with a fenced block when the source should travel inside the document, and either is drawn as an image. The design, with its own numbered decisions, is `docs/diagrams-design.md`, and the Editor's design (decision 24) is built with it in view.

26. **The desktop is windowed only** (2026-11-03, Paul: the Pages view served no purpose). The desktop no longer has a Pages view, the switch between Windowed and Pages is gone, and so is the list of applications at `/pages`, which now leads to the desktop. This replaces the Classic view decision 3 carried over from parkscomputing.com. An application's page of its own is its subdomain, `{slug}.yavc.app`, which is where its window's Open as a Page button already led, so an application has one window form and one page form. `yavc.app/{slug}` for an application now leads to the desktop with that application's window open, so a link kept from the Pages view, or one in an article, still arrives. A site page (help, the privacy policy, the terms, the author's page) keeps its own address on the site as a page, because it has no subdomain, and its window's Open as a Page button leads there. A link inside a page drawn in a window that leads to another of the site's windows carries PUDL's `data-win-open`, so on the desktop it opens that window beside the others and never leaves the desktop. Where there are no windows, as on the Terminal's own page, the Terminal sends an application to its subdomain.

27. **Freeform diagrams are JSON Canvas files** (2026-11-04, Paul). The D2 editor lays out every diagram itself, so it cannot place shapes where they are put. Paul chose a second, freeform editor beside it rather than one compromise, and asked that it not become a language of the site's own. A freeform diagram is therefore a `something.canvas` file in JSON Canvas 1.0, an open format published by Obsidian, opened by Diagrams and drawn by the site's own renderer; what the format lacks, chiefly shapes, is one documented extension that degrades to the format when another application drops it. `docs/canvas-design.md` holds the design.

28. **The Markdown dialect is a stated specification** (2026-11-04, Paul). Decks, documents and the site's pages are Markdown with the site's shortcodes, which is a dialect of Markdown, and Paul asked that it be stated rather than left implied by the engine. `docs/markdown-dialect.md` defines it as version 1, with the catalogue of shortcodes, the two profiles (decks and documents), and the rule for when a change needs a new version; `TestDialectCatalogue` fails when the engine knows a shortcode the specification does not list.

29. **Canvas edits have a separate agent action** (2026-11-04). `yavc.diagrams/edit@1` keeps its D2 keys and operations. JSON Canvas uses `canvas-edit@1`, because moving a node means changing coordinates and a connector has its own ID rather than a D2 expression. The action uses the same validated model edits and undo history as the drawing; `canvas-view@1` provides selection, pan, zoom, fit and actual size without changing the text. A `kind` distinguishes a node from an edge when their IDs coincide, which JSON Canvas permits. The editing controls and camera follow `docs/canvas-design.md`, decisions 15 and 16.

30. **Connector endpoints remain in JSON Canvas** (2026-11-04). Paul requested draggable line ends, free ends and automatic anchors that adapt as nodes move. A free end uses a zero-sized empty text node; its optional `yavc.anchor` marker identifies it as an editor-owned point. The line retains JSON Canvas's required endpoint references. Automatic attachments omit the standard side property, while explicit side attachments retain it. `docs/canvas-design.md`, decisions 18 and 19, states the interaction and ownership rules.

31. **Standalone applications retain their page when opening site information** (2026-11-04, Paul). Help, the author, agent guidance, privacy and terms open in PUDL floating windows over the running application. Their open, minimised and active state uses the existing window query parameters, so reload restores the windows. About dialogs use addresses on the application's own origin and retain its query parameters. Back and Forward follow the dialog address without restarting the application.

32. **Canvas text position can be set on either axis** (2026-11-04, Paul). The inspector and existing canvas edit action expose horizontal and vertical alignment independently, with optional properties in the documented extension and shared resolution for live text and SVG exports. Shape Default preserves existing files' placement. Drawing tools move into a submenu so the ribbon offers a compact picker instead of a large segmented control. `docs/canvas-design.md`, decisions 21 and 22, states both contracts.

33. **Diagram editing commands share the Edit menu** (2026-11-04, Paul). Tidy the Text, Draw Again and Copy as Embed join the existing Edit commands, removing the separate Diagram menu and ribbon tab. The ordinary toolbar follows the same grouping, with picture exports under File.

34. **Canvas selections can contain several typed items** (2026-11-04, Paul). Modifier clicks, a marquee around nodes, Select All Items and the keyboard-accessible Select Items dialog build the selection. The inspector exposes the intersection of supported properties, distinguishes mixed values and applies edits atomically. Moving selected nodes carries contained group members once. Canvas action requests accept typed item arrays while retaining the existing single-item form. `docs/canvas-design.md`, decision 23, records the contract.

35. **The inspector uses a resizable pane and compact choices** (2026-11-04, Paul). A PUDL splitter adjusts the drawing/inspector division and remembers its proportion. Horizontal and vertical text alignment, Line Style and connector Route use segmented controls. Shapes, arrowheads and connector sides remain menu choices. Color uses the shared native picker with presets and an explicit default reset; control labels use American English. Language-server feasibility is assessed separately in `docs/language-services-design.md`; this batch installs no LSP transport.

36. **JSON language assistance is shared and browser-local** (2026-11-04, Paul). Editor and Diagrams use one LSP integration in `apps/md-editor`, with the official CodeMirror client and a bundled JSON language server in a worker. JSON Canvas remains the format, and its schema includes the yavc extension. Completion, hover, revisioned diagnostics and guarded formatting run without sending source outside the browser. D2 retains its existing completion provider. `docs/language-services-design.md` records the scope, lifecycle and build contracts.

37. **Canvas editing features ship in a combined round** (2026-11-05, Paul). Direct shape text editing, independent fill and outline colors, diagram-level Inspector settings and freeform starter templates are implemented together. The Inspector keeps a pixel width when the main split moves, and its choices fold without breaking labels. Inline edits immediately enter the source and its history; document settings and colors use additive JSON Canvas extension properties with matching schema assistance. Save, Save As and agent saves share ordering and acknowledgement guards for the live editing lifecycle. `docs/canvas-design.md`, decisions 27 through 32, records the contracts and limits.

38. **README badges and image alignment use the shared Markdown pipeline** (2026-11-05, Paul referenced the Dinah README). Linked badge images use ordinary Markdown and the existing HTTPS image policy. Local-image normalization retains the recognized left/right alignment values, and shared page CSS gives local and remote images the same float/clear behavior. Existing class-based right alignment remains available for images on their own line. Image handling retains the existing sanitizer and resource resolver. `docs/markdown-dialect.md` records the supported markup.

39. **Editing productivity and save safety ship together** (2026-11-05, Paul). The next combined batch adds the Canvas Outline, node alignment/distribution and keyboard access between panes, fixes stretched Inspector controls and makes Theme Default visibly remove the background override. Editor saves use the same originating-document and ordered-acknowledgement policy as Diagrams, including inactive renames and recovery of newer drafts. The host adapter, offline package and desktop-webview acceptance remain separate migration work. `docs/canvas-design.md`, decisions 33 through 35, and `docs/editor-follow-ups.md` record the scope.

40. **Common toolbars use applet commands and host preferences** (2026-11-05, Paul). Diagrams, Editor/Docs and Slides share one customizable common-command toolbar below the topbar. PUDL renders command state, menus and responsive folding from the applet's existing command table. The host supplies the optional toolbar controller and stores per-app command order and visibility through its configuration service. Each applet keeps its existing toolbar as a fallback for hosts without that capability. The customization form supports adding, removing and moving commands and separators, restoring defaults, and choosing whether the bar remains visible with the ribbon. `docs/command-toolbar-design.md` records the interface and lifecycle.

41. **Start uses the released PUDL control** (2026-11-05, Paul). PUDL 0.98.0 supplies the catalog, category filtering, search, splitter and keyboard interaction. The host places Start in the desktop taskbar and standalone headers, supplies real application links and maintains its query and category in namespaced URL parameters. The host categorizes installed applications without changing their package manifests. Create, Tools, Barcodes, Learning, Games and Settings may overlap; new unassigned packages appear under Other. Every installed application appears once in All. The host uses the documented `pudlStart` API and preserves current desktop windows when launching an application.

42. **Start replaces the desktop application sidebar** (2026-11-05, Paul). The desktop gives its full working width to windows. Start provides application discovery and search, so the former application list, resize handle, taskbar toggle and View command are removed. Existing window URLs and applet-owned panes keep their behavior. Legacy sidebar scroll snapshots are ignored.

43. **Document styles share one compiler and editing surface** (2026-11-05, Paul approved the styles batch). Editor and Slides apply complete top-level `{{style}}` blocks and a local shared CSS file through the same scoped, contained controller. Both use a CodeMirror CSS editor with diagnostics and source-preserving block replacements, and their style pickers list classes from accepted CSS. A stylesheet dialog belongs to its originating document and app lifetime; pending saves freeze its draft and failures retain it. Slides uses the same compiled CSS and scope keys for thumbnails, presenting and export. Custom macro expansion remains the next batch. `docs/docs-design.md`, decisions 20 through 22, records the current CSS restrictions and lifecycle.

44. **Editor structure edits use Markdown source ranges** (2026-11-05). The Markdown engine supplies Outline heading and section ranges so source navigation and section moves share the same interpretation of code, front matter and shortcode declarations. Editor performs each section move as one source transaction. Quote editing and table column alignment belong to the shared page view, preserving untouched source and exposing the same controls in Slides. `docs/docs-design.md`, decision 25, records the boundaries. Word/PDF export and export exclusions remain separately planned.

45. **Office exports prepare one shared document before writing files** (2026-11-05). Editor downloads editable DOCX and selectable-text PDF through browser-local writers. Both consume the same prepared document, after exclusion pruning and before asset discovery or pagination. Slides uses the same engine pruning for audience output, Office/HTML exports and synchronized printing. `docs/docs-design.md`, decision 26, records the initial formatting coverage, bundled fonts and explicit refusals. Source Markdown stays private to the browser and is not embedded in the artifacts.

46. **Exports carry explicit document paper colors** (2026-11-05). Export preparation starts with white paper and neutral dark ink, independently of the app theme. Shared and inline document styles override those defaults in the established order. Both writers serialize the resolved paper color instead of relying on the reader's default. `docs/docs-design.md`, decision 27, records the color boundary and regression evidence.

47. **Editor gains a paginated Document view** (2026-11-06). Documents remain Markdown with one editing history. Physical page settings are shared by the editable page layout, printing and Office exports. The first stage breaks between whole blocks and refuses printing of oversized blocks; finer pagination and document furniture remain later work. Decisions 28 and 29 in `docs/docs-design.md` define the implementation boundaries.

48. **Document files retain physical layout across rendered views** (2026-11-06, Paul). A `.docs.md` file keeps its paper size and margins in Visual, Split and Preview after visiting Text. Ordinary Markdown keeps its fluid Visual view, with Document available explicitly. Page Setup uses a bundled registry of standard paper sizes, editable custom dimensions and individual or linked margins. Decisions 30 and 31 in `docs/docs-design.md` record the file representation and validation.

49. **The default Editor toolbar includes its view selector** (2026-11-06, Paul). The removable View item displays Document, Visual, Text, Split and Preview in that order. ## Addresses

`yavc.app` serves the desktop, which is windowed only (decision 26). A window's content comes from `/win/{key}`. `yavc.app/{slug}` opens the desktop with that application's window, or draws a site page as a page of its own. `{slug}.yavc.app` serves the same application standalone, and it is the application's page form. The engine answers both from one deployment: a wildcard DNS record points every subdomain at it, and the engine reads the host header to choose the standalone layout for the application whose slug matches. A subdomain whose slug matches no application redirects to the desktop.

Docs is an independent package at `docs.yavc.app`, with its own desktop key and recovery namespace (decision 75). The former Editor alias is removed. The engine retains the alias mechanism for future separately declared aliases.

The PUDL applet definition's `page` field for each application is its subdomain address, so Open as a page from a window goes to `{slug}.yavc.app`, and `ownsUrl` is true only there.

## State and identity

The engine keeps a key-value store of application state per session. A session is an opaque random identifier in a cookie on `.yavc.app`, `HttpOnly`, `Secure`, `SameSite=Lax`, created on the first request that needs one. The store holds, per session, each application's state string as the applet contract defines it, shared preferences, the open windows of the desktop, and the reader's theme and skin. Guest home files remain browser-local and origin-specific under decision 11; sharing session preferences does not share those files.

PUDL keeps theme and skin in local storage under `pudl-theme` and `pudl-skin`, per origin. The host page seeds those keys from the session before `pudl-theme.js` runs, so a skin chosen on the desktop is the skin on every subdomain.

The retention period is 90 days, set by the engine's `-retain` flag. A session that has not been seen for that long is deleted with its state, and reading counts as being seen (decision 20). The privacy page says so in plain words.

The administrator signs in to a separate session. Privileged operations use the pattern parkscomputing.com settled on, passkeys with a fresh tap for a change to the live site, reimplemented in Go. Before the administrator's mount is built, the server-file branch of the Editor's `onFsChange` in `workspace.js` must ignore a read that began before a save, with the version and saving counters of decision 161, since it takes the answer of a read without checking that the tab was saved while it ran.

## The engine

The engine is one Go binary. It serves static files for the desktop, PUDL and each application; the session store; the site tree from the navigation file; the virtual file system's server mounts for the administrator; the page editor's read and write endpoints; and, for the RSS reader, a fetch proxy for feeds whose origins do not allow cross-origin reads.

Representations follow the REST principles in the architectural document. An illegal action is absent from the representation rather than refused. Every state the desktop can show has an address.

The parkscomputing.com engine's endpoints that the carried-over designs expect are the starting inventory for the Go engine: the site tree, the texts of pages by slug, and the administrator's mount for reading, writing, moving and deleting files. Their shapes are reimplemented, not copied.

## Applications are packages, and the engine is a host

Every application is a PUDL applet package in the format defined by the pudl-applet-packages repository (`C:\Users\paul\source\repos\pudl-applet-packages`). A package is a folder with an `applet.json` manifest, a script that calls `pudlApplets.register`, a stylesheet, a page body and optional actions, help and vendored libraries. The engine installs a package by having its folder under `applets/`, scans the manifests at startup, and generates from them what parkscomputing.com's `js/applets.js` writes by hand: each applet's `define()`, its standalone page, its window size, its launcher entry and its continuity. Adding an application is copying a folder.

The engine gives packages the host interface, `window.pudlHost`, built with the host kit from that repository. The members and what yavc.app provides for each:

| Member | yavc.app |
|---|---|
| `identity`, `action`, `pages`, `pudl` | From the kit, with pages at `{slug}.yavc.app` and `/{slug}` |
| `snapshot` | parkscomputing.com's snapshot script as it is, per browser tab in session storage; a snapshot is what a reload loses and no link should carry, so it belongs to the tab, while continuity and settings belong to the session |
| `fs` | The virtual file system, with a guest's home in the browser's local storage (decision 11) and, with accounts later, a home on the server and the administrator's mounts; Open and Save as dialogs |
| `config` | Per-applet settings in the session store |
| `service(name)` | A map of the engine's services; `rss-fetch` for the feed reader, `score-library` for the sight reader, others as applications need them |
| `actions.run` | PUDL's action broker |
| `fetch` | Same-origin fetch with the engine's forgery token on writes |

The games, the tools and the barcode applets already exist as packages in their own repositories, each released as a `dist/` folder: pudl-sudoku, pudl-conway, pudl-dice, pudl-sight-reader, pudl-poker, pudl-barcodes (tool, scanner, flash cards) and pudl-tools (diff, theme studio). PUDLSplash is the arcade collection, where Space Invaders and Asteroids belong. None of these is ported; each is installed at a tagged release. A package written for yavc.app alone may live in this repository under `apps/`, in the same format, and moves to a repository of its own when another host wants it.

Manifests stay JSON, since the package format is shared with parkscomputing.com and PUDL Desktop and is not this project's to change. Decision 4 applies to the engine's own files and representations.

## Appearance

The reader's appearance has three independent choices, as Dinah Desktop implements them: the skin (`data-skin`, from the PUDL release's catalogue in `pudl-skins.json`), the colour theme (`data-palette`, PUDL's companion themes and any of the site's own), and the mode, light, dark or system (`data-theme`). The engine owns all three in the session store, and the page is drawn on the server with the choices already on the root element and `data-pudl-persistence="host"` set before PUDL's scripts load, so there is no wrong-skin flash and no second store in local storage. Every admitted skin's stylesheet is linked in the head. The Settings applet offers the three choices and View offers mode and theme, as Dinah's menus do. The list of skins is read from the release, never written into the engine.

A theme editor of the site's own, with personal themes as Dinah has them, is not in the first release; the theme studio package covers editing a palette until then.

HTML supplies completion, hover and formatting; the upstream service does not expose general validation. 92. **Physical pages can split prose without splitting the source model** (2026-11-09). Measured line units extend the existing widget planner through paragraphs and list content, while table rows become separate units. The first and last two lines form protected groups. 93. **Footnotes remain editable source with page-owned placement** (2026-11-09). Public Goldmark parser interfaces recognize references and definitions while the project retains definition positions, unused material and source spelling. 94. **Source history owns reversible line-ending provenance** (2026-11-09). This avoids relying on custom effects surviving CodeMirror's history JSON, which its documented interface does not promise. Untouched separators remain exact; inserted separators follow the surrounding source; Undo, Redo and recovery restore recorded provenance. Current draft endings survive the existing history-size fallback. Encoding-aware persistence remains an independently negotiated host capability. `docs/source-history-design.md` defines the implementation and recovery boundary.

95. **Encoding-aware saves negotiate resource authority version 2** (2026-11-09). Source text excludes the encoding signature, and issued snapshots retain an explicit encoding and signature flag. Version 2 read/write/create/Save As operations preserve that format and revision, while version 1 hosts retain their existing UTF-8 interface. Guest UTF-16 resources remain byte records so older VFS clients fail closed. Replacement bytes and the revision-bearing file record commit in one IndexedDB transaction. Recovery retains format metadata and refuses an unsafe writable rebase of legacy signature-bearing drafts. `docs/encoded-resources-contract.md` defines the compatibility and validation rules.

96. **Office imports create reviewed native copies** (2026-11-09). DOCX import uses pinned Mammoth 1.13.0 in a disposable worker after bounded ZIP expansion. Embedded style maps and external file access are disabled. The resulting inert HTML passes through the shared cleaner and page schema before the Markdown serializer; imported images and footnotes receive explicit native representations. Unsupported layout, review metadata and omitted assets appear in a loss report before a new unsaved document is created. The original Office resource is never overwritten. PPTX import follows the same copy and reporting policy. `docs/office-import-design.md` defines limits and conversion behavior.

97. **Document review edits the persisted CriticMarkup source** (2026-11-09). Review uses the five forms chosen in Docs design decision 11. A Markdown-aware catalog supplies exact source ranges and refuses malformed, nested or stale edits. Proposals and comments survive Save, reload and export preparation. Individual and whole-document Accept/Reject operations each form one source-history transaction. Review dialogs retain the initiating source revision and selection. The source remains the authority for both the rich surface and the review list; rendered HTML attributes cannot authorize an edit. `docs/document-review-design.md` records parsing, editing and output policy.

107. **Guest files have individual database entries and byte contents** (2026-11-10, Paul). The guest authority moves from a serialized home document to `entries`, `contents` and `state` stores in the `yavc-vfs` IndexedDB database. Every text or binary file references immutable byte contents; paths, revisions and directory metadata remain structured records. Consumers load contents on demand. Ordinary resource saves compare one file revision and commit its contents, metadata and usage in one transaction. Tree operations compare the directory generation. Defaults allow 100 MiB per stored file, 1 GiB of live file contents and 10 MiB of editable source; hosts can supply a storage policy. 112. **An HTML table is edited as a table and written back as HTML** (2026-11-10). A page brought in from a wiki holds tables a pipe table cannot write: merged cells, coloured cells, a heading row below the first. Such a table arrives as an HTML block, which Visual view showed as a source block nobody could type in. An HTML block that is exactly one table of a strict shape is now read as the page's table (`internal/pageview/rawtable.go`). Its children are colgroup, thead, tbody and tr, its rows hold th and td, its spans are whole numbers, and a cell holds inline content, or one plain paragraph of it. Strong, emphasis, underline, strike, code, mark, superscript, subscript, a link with only an address and a line break are read as the page's marks and breaks; any other inline element is one piece, kept as written and drawn as safe-html allows. A block element in a cell leaves the table a source block. Everything else is kept, that is the attributes of the table, its rows and its cells in their order, the column group, and whether the rows were in a head or a body. An untouched table is written back byte for byte. A changed one is written afresh with the kept attributes, its text escaped, and a span of one left out unless it was written, and it is never written as a pipe table. The guard is that the table read and written straight back must equal its markup, token for token with the space between table parts ignored, or it stays a source block, so opening a page loses nothing. The same reading serves a host container whose catalog entry says its body is literal markup (`literal: true`, `docs/host-shortcodes-contract.md`): the body is read whole, blank lines included, which Markdown would split at the first blank line; one table in it is edited as a bare table with the container's two lines kept around it, and any other literal body is one source block in the container's box. The table commands Markdown cannot hold, merging and splitting cells, heading rows, columns and cells, and a cell's colour, turn a pipe table into an HTML table with no attributes of its own, and the page says so once. A copy of an HTML table pasted from the page's own DOM keeps its attributes but not its column group, which the engine writes verbatim and therefore trusts only when read from the text; the engine also refuses to write a column group or a kept piece that is not one well formed element, and an attribute whose name could write markup.

113. **Changing the view keeps the reader's place** (2026-11-10). The text's caret is the one place every view shares. When the page is left for Text, Split or Preview, the page writes itself to the text and then maps its caret to the text: the exact spot where the text is exactly the page (the sentinel mapping `sourceSelection` already does for review), and otherwise the start of the block the caret is in, from the blocks' texts and the text before each. The text's caret and scroll go there, and Preview scrolls to the block whose first line is at or before that line. When the page is turned on from Text or Preview, it opens at the block that holds the text's caret, worked out the same way, and scrolls it into view; a page built again for a change to the text keeps its own scroll as before.

114. **The contents list reads the whole document and a wiki's spellings** (2026-11-10). A container's body is rendered on its own for the page view, so `{{toc}}` inside one found no headings and drew nothing. The body's rendering now has the whole document in reach (`shortcodes.MacroRegistry.Within`, `preview.Whole`), so a shortcode that reads the document reads all of it wherever it stands; and the page reads the whole text again, rather than a slice, when a change to the text touches a heading or a contents list, since any other change leaves every list right. The list reads `minLevel` and `maxLevel` as other spellings of `min` and `max`; when either is written an absent bound is 1 or 6, since the spelling is a wiki's, so the wiki's defaults apply, while `min` and `max` keep 2 and 3. Arguments the list does not know, a wiki's `type` and `outline`, are left be, and the source stays as written.

115. **A host can name the attribute that records a cell's colour** (2026-11-10). The engine only carries the field; the page does the work, from the container's opening line the table keeps. A bare HTML table has the style alone. Paul approved the field on 10 November.

117. **A host can say which classes stand for a cell's colour** (2026-11-10). A wiki's own editor also marks a coloured cell with a class such as `highlight-grey`, which Cell Color left behind when it changed or cleared the colour. A literal container's catalog entry may say `colorClassPrefix`, and in that container's tables Cell Color removes every class of the cell that begins with it, and the class attribute when no class is left. Nothing is added, other classes keep their order, and a cell that is not recoloured is untouched. Paul approved the field on 10 November. 118. **Text in brackets is edited on the page where the document defines no references** (2026-11-10). Paul found that a paragraph with a citation written `[S2]` could not be edited in Visual view. The writer escapes an opening bracket that has a closing one after it, because `[S2]` is a link wherever the document defines `S2` as a reference, which a part read on its own cannot see. A paragraph with such text therefore never came back as it was read, and it was kept as source. The rule is now decided for the whole document. Where no line could define a link reference or a footnote, text in brackets is only text: the part is read as rich text with its source kept, and a changed block is written with the escape left out wherever the text reads the same without it, which is checked by reading both. A bracket that would then open a link, a picture or a definition keeps its escape, and so does a task's box. A document with a definition keeps the careful behaviour, and the page reads the whole text again when a change touches one.

119. **A host can keep a cell's colour in a shortcode, so a pipe table stays one** (2026-11-10, approved by Paul). Cell Color turned a pipe table into an HTML table, because Markdown has nowhere to keep a colour. A host that keeps it in an inline shortcode of its own, written first in the cell, marks that catalogue entry `cellColor: true`. On a pipe table Cell Color then asks with the host's own form, so the host refuses a colour it does not know beside its field, and writes, changes or removes that shortcode first in each selected cell. The dialog starts from the shortcode in the caret's cell. An HTML table keeps decision 115's style and attribute. A change that needs an HTML table, merging or splitting cells or a heading cell, is refused with a message while a cell has the host's colour, since a shortcode cannot be written in an HTML cell and losing a colour without telling the reader is the worse failure. The editor does not paint the cell; the host's stylesheet does, so one place decides how the host's shortcode looks.

120. **A host can say a document has no saved location, and a referenced file's reader is told which document asks** (2026-11-10). In a host that keeps every new document as a draft of its own, the applets saw a resource they could write to, so Save wrote the draft and nothing visible happened; only Save As gave the document a place. A host's read and write results may now say `needsLocation: true`, and Save then opens Save As in Editor, Docs, Slides and Diagrams, where the host offers it. The flag is on the snapshot the resource client issues, so it goes when Save As returns a placed resource. Separately, `pudlHost.fs.readText` is passed `options.document`, the owning document's resource or null, so a host can keep a reference inside the document's own workspace and stop watching a folder when the document closes.

121. **A host can run the slide show in a window of its own** (2026-11-10, approved by Paul). In a desktop host the show was an element of the host's one window made full screen, and the presenter view was a window inside it, so the presenter could not be kept on one display while the audience watched another. Version 2 of the presentation capability lets the host open the show elsewhere. Slides asks with `openShow` and is given a port; the host's second window mounts Slides with `show=1`, which draws only the deck it is sent. The editing window keeps the deck and stays as it is. It sends the deck's text and the slide to show, and it receives the slide the show has moved to and the show's request to end. The messages are versioned JSON, which a host can pass between two processes, where a `BroadcastChannel` is not documented to work. A port was chosen over passing the presenter's channel by name because it makes the relay the host's own, lets the host report when the connection closes, and leaves Slides knowing nothing of how the two pages are joined. `openShow` must settle within a second, since the fall back is full screen in this window, which a browser grants only to a recent press. A show that ends because its window closed is said in the status line and is not replaced by full screen. A deck too large to send ends the show with a message in the editing window. The status bar says a show is running for as long as it is. The contract is `docs/presentation-contract.md`.

Only a change event of the kind `settings` makes the files be read again: the change event says its kind, the settings files are kept apart from the other files in the file system and raise `settings` when they change here or in another tab, and the save of an ordinary file, which a large document does at every save, raises `home`, so it costs the settings files nothing (the lead asked that it not grow with the size of the folder). `scripts/test-config-watch.cjs` makes another write to the file while a save of it is under way and checks that the settings and the listeners have it, in three browsers; it fails before either part of the change, and it counts the reads of the settings file while five ordinary files are saved, which were five before the filter and are none after.
194. **A language session closed during its start is cancelled quietly** (2026-11-14, the lead's task, found by Dinah Team Lead). Closing a Diagrams window while the language service was still starting left an unhandled rejection in the console, `{code: -32800, message: "Language session ended."}`. The bridge ends an unanswered start with that error when the session stops, which the client's start promise handles, but the language client also queues the notices that open and close a file behind that promise, and each of those derived promises is rejected as well with no one to catch it. I reproduced it in Chromium, Firefox and WebKit by opening an editor with the language extension, letting it open its file, and disposing the session before the server answered. The bridge now marks exactly that rejection as handled, with the page's documented `unhandledrejection` event and `preventDefault`, and leaves every other unhandled rejection alone. A start that was cancelled is not a failure, so no notice is shown. `scripts/test-language-session-end.cjs` checks both halves in three browsers, that nothing is left after a cancelled start and that an unrelated unhandled rejection is still reported; it fails before the change.
195. **A read-only instance says whether the place it was given was used** (2026-11-14, PFO's request through the lead, low priority). A host gives a read-only Docs instance a place as `data-docs-position`, and the instance opens there when the text the place names is still in the note; when the note has changed it opens at the top and said nothing, so PFO could not tell the reader that the note had changed since they last read it. The instance now keeps `placeUsed`, `true` when it opened at the place, `false` when the text is gone or the string cannot be read, and `null` when none was given or it has not been tried, and gives it in three ways that suit a host with one instance or with several: the `placeUsed` field of the `position@1` result, `detail.placeUsed` of the `yavc-docs-position` event, and a `yavc-docs-place` event on the root that says it once when the place is tried. They are documented in `docs/editing-settings-contract.md`, under "A place in the text". `scripts/test-docs-read-only.cjs` checks a place that is used, one whose text is gone, a string that cannot be read and none given, by all three, in three browsers.
128. **A canvas written from a screen is measured against the screen, and the format takes what the measurement shows** (2026-11-12, from the receiving product's measurement, within the approach Paul approved the day before). The receiving product's screen viewer wrote 72 screens and tableaus as canvas files and compared each picture with its own, pixel by pixel. Between 1.4 and 8.6 percent of pixels differed, nearly all at letter edges and one-pixel borders. Two causes were faults. A font family was written unquoted, so a name the format allows and CSS does not read as an identifier lost the whole family list; families are now quoted. A picture's lines were broken by an estimate of each letter's width, which cut a label in a box exactly as wide as its letters; the width is now measured where there is a page, and an estimate no longer cuts a word it is not clearly sure of. Three were gaps, each closed by an additive version 1 property (`docs/canvas-extension.md`): `lineHeight`, `outlinePosition` with `inside` for an outline drawn as a CSS border is, and `noFill` for an outline with nothing inside it. They were taken in the order the numbers gave. A picture inside the file, a radius for each corner and padding for each side were counted and left, since they change fewer pixels and a picture in the file needs its own limits and checks. The first baseline of a text is now worked out from the line height, as half the extra space and then 0.85 of the size, which gives the old place at the old line height of 1.3 and the browser's place at others. A second measurement the same night, with the new properties written, brought the differing pixels down to between 0.6 and 3.8 percent and showed what was left: a text font's baseline a fraction of a pixel low, and a symbol font's one to three pixels high, because 0.85 is not every font's ascent. Where there is a page the baseline now comes from the font's own ascent and descent, by the rule CSS states for a line box, with each rounded to a whole pixel. The rounding is this renderer's own choice of where to put text, made to agree with what the measurement saw; the drawing is right by CSS's rule without it, and nothing depends on how a browser rounds. An estimate of width is now trusted only beyond a fifth for a new line as well as for a cut, since a canvas written from a screen has boxes as tight as the screen's. `paddingSides` was added because 69 texts on the measured screens had to stay separate nodes beside their boxes without it. A host may also offer `openDiagram` (`docs/content-workspace-contract.md`), so that it need not stand in for PUDL's own functions to open a diagram from a document. The last two counted gaps followed in the next release. A picture node may keep its picture in the file as a data address, with a limit of 256 KiB and a check of its first bytes done when the file is read, since nothing else stands between the file and the drawing for such a picture; it is drawn as image data inside an `image` element as every picture is. `radiusCorners` gives each corner its own radius, drawn as a path.

## Open questions

1. **XferLang version.** No Go implementation exists; the repository has the C# library and a Rust port. The parkscomputing.com navigation file is in the 0.15 form, and a 1.0 reboot is under way. The Go library should implement 1.0 if its grammar is settled; confirm with the XferLang Reboot work before starting.
2. **Untrusted previews.** If the editor previews HTML written by a reader, or the RSS reader renders feed content, that content needs an origin of its own. A single sandbox origin, or a sandboxed iframe, is the intended answer; decide when the editor is ported.
3. **Session cookie and consent.** The anonymous session exists only to keep state the reader asked the site to keep, which is the strictly-necessary case, so no consent banner is planned. The privacy page must still describe it, with the retention period. Revisit if the session is ever used for anything else.
4. **A page-sized view.** Paul raised sizing the Editor's page to a printed page, as a word processor does, when the Visual view's wrapping was settled (decision 15). It would be a view of its own beside Visual, with the page size and margins from the document or the settings, and it bears on the PDF export of documents. Designed on 2026-11-03 as the Document view of `docs/docs-design.md` (decision 24).
5. **A notification list and a taskbar item for background work** (raised 2026-11-03; Paul said one may be added where the need is strong enough). PUDL offers toasts for passing confirmations and a status area for what runs in the background, and a list of notifications would be built from its persistent sidebar. The need is not strong for any one application: each shows its own faults as notices where they happen. It becomes strong with agents. An agent's actions run in whichever page of the person's is in front (docs/agents-design.md, decision 7), possibly in a window the person is not looking at, and today nothing keeps a record of what an agent did once its dialog has closed. The recommendation is one site-wide pair, built when the agents' work grows past single actions. A status-area item would show how many agent actions are running and whether one waits for permission. A notification list would record each finished action and each background event (a diagram redrawn because its file changed, an export finished), with a link to the file or window concerned. Applications would post to it through PUDL's `notification.post` capability, which the agents design already names. Diagrams and the Editor would use it rather than inventing their own.
