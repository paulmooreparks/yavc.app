# Resource recovery contract

The resource client and the snapshot service remain separate host capabilities. Recovery stores an original revision alongside unsaved text; it does not create another file authority. The shared recovery helper has no persistence or filesystem access of its own.

## Restoring a draft

A version 2 Diagrams snapshot contains its tab state and, for each bound resource, a version 1 baseline with `resource` and `revision`. It retains draft text for dirty tabs and unbound drafts. A clean bound tab can read its current contents again. Baselines come from snapshots issued by the same resource client; the public `baseline()` helper refuses arbitrary copied objects.

Encoding-aware resource authorities now produce version 2 baselines with `encoding` and `bom` alongside the resource and revision. Recovery compares that format before issuing a writable snapshot. The workspace snapshot retains its version 2 envelope and keeps the tab's format for unbound copies. This is a distinct version from the resource authority and baseline; [the encoded-resource contract](encoded-resources-contract.md) describes their roles.

The helper validates identities, versions, text size and tab count before snapshot registration. A saved baseline must name its tab's resource. The payload supports at most 512 tabs, 4 MiB of text per draft and 8 MiB across draft texts. These are input bounds, not a promise of browser storage capacity. Capture validates the same bounds before writing, so the service cannot acknowledge a payload it would refuse to restore.

On restore, a dirty draft can obtain an issued resource snapshot only when a fresh host read returns the original revision. Its later save still performs the host's conditional comparison. If the file changed, the draft retains its original baseline and text without obtaining a writable snapshot. A failed read also retains both, allowing another recovery attempt. An older dirty snapshot without a baseline keeps its text but cannot borrow the current file's revision. Clean tabs reread the current resource normally.

Diagrams displays a warning for those recovered conflicts, disables Save with a reason, and retains source download. Reopening or discarding the draft remains an explicit user action. A host can now supply the optional Save As operation in `content-creation-contract.md`; conflicted drafts can preserve a copy through it. Hosts without that operation direct the person to source download. Guest Diagrams adopts that capability with the read-only command policy described in `diagram-resource-adoption.md`. Editor and Slides now use the same recovery baseline rules, as recorded in `editor-slides-resource-adoption.md`. Routing, source preservation and package extraction remain gates for the complete Docs/Editor split.

Revision tokens must not identify different text states of one resource. Resource identities remain scoped to the host authority and workspace, and the host rechecks write permission at execution. Recovery metadata does not confer access or replace conditional writes.

## Snapshot service version 2

The yavc-owned snapshot extension reports `version: 2`. Existing `join(root, take)` callers remain supported. A resource-aware caller uses `join(root, take, {validate})`; its synchronous validator runs before any provider is registered or another snapshot key is removed. Unsupported payloads therefore retain their previous stored copies and cannot be replaced by an empty startup snapshot.

Joining selects the newest applicable snapshot but retains alternate keys until a replacement write succeeds. Disposal or startup failure before that write leaves the original copy available. A failed replacement also retains it. Cleanup happens only after the destination acknowledges storage. Resource-aware startup returns the original kept value while it is still restoring, so a background snapshot cannot capture a half-restored workspace.

The returned handle adds synchronous `flush()`, which reports whether the latest value was stored. Serialization and quota failures return false and preserve the previous stored snapshot. A failed snapshot remains dirty for a later attempt. A left handle cannot flush. Diagrams' reload guard calls this acknowledgement before claiming unsaved work is retained; a failed flush keeps the normal browser unsaved-work warning available.

This is a yavc host extension, not a claim that PUDL publishes this recovery contract. Another host must implement the documented version before combining recovery with the experimental resource capability. Legacy snapshot implementations are refused before registration. The installed resource adopters are recorded in `diagram-resource-adoption.md` and `editor-slides-resource-adoption.md`; extraction into another application's host remains a separate acceptance gate.

### Telling the host of a draft

A host that keeps drafts learns of them through the handle that `join` returned, and the applet keeps three promises about it in every view of Docs and Editor. The first is that the applet calls `changed()` for each edit to the text of an open document at the moment of the edit, and not after a pause, except while an input method is composing, which the third promise covers. The second is that the function the applet gave to `join`, called `take()` here, returns the current text, with every edit made so far. A handle that has not heard `changed()` since the host last took a snapshot therefore holds nothing newer. The host may call `take()` from inside `changed()`; the second call finds nothing waiting and returns, so there is no loop. Since the snapshot also holds each tab's view and caret, the applet may call `changed()` when the person switches view or moves the caret, Split's mapping of the caret into the other pane included, with the text unchanged; laying the document out in pages, a resize and the settling of the layout change nothing in the snapshot and do not call it (`scripts/test-pagination-preserves.cjs`).

The rich view of Docs converts its edits to Markdown after a pause of 300 milliseconds. When the host calls `take()` while an edit is waiting for that pause, the applet makes the conversion then and there, synchronously, which is the same conversion the pause would have made and not a second path. The call leaves the page, the caret and the undo history as they were. If the engine that converts the page has not loaded yet, which can happen only in the first moment after the page opens, `take()` returns the text without the page's latest edit and the pause tries again; when its conversion succeeds it writes the text and calls `changed()`, so a `take()` after the last `changed()` is current.

The third promise is about an input method that is composing, which is text typed in several steps before it is committed, as some keyboards make a tone mark. While it composes, `take()` may or may not include the characters not yet committed. Once the composition ends, the host is told of any change it made, so a `take()` after the last `changed()` returns the committed text. A host therefore needs no knowledge of which view is open.

How each view keeps that promise is information and not part of it. The rich view of Docs does not convert the page in the middle of a composition, because that can break the composition, so during one `take()` returns the text as it was before it began, and `changed()` is called when it ends. The Markdown view has no conversion to hold back. Its text is the text of the editing area, which includes the characters being composed, so `take()` returns them, and `changed()` is called as that text changes.

The argument `true` that the page view passes to its own `changed` function is an exchange between the page and the workspace inside the applet. It is not part of the host contract, and a host never sees it.

`scripts/test-docs-draft-notification.cjs` checks all of this in the one-page host: each key in both views, a run of keys with no pause, a `take()` in the middle of typing that must leave the page, the caret and undo as they were, and a composition driven through the Chrome DevTools protocol, after which what a host that calls `take()` on each `changed()` last stored must equal what `take()` returns. Only Chromium can drive a composition from a test, so Firefox and WebKit run every check but that one. The test checks the third promise in both views and does not check how each view keeps it.

## Remembering a closed workspace

The yavc snapshot host advertises `remembersClosed: true`. A primary applet instance can opt into `join(root, take, {remember: true, validate})`. The host stores each live registration's workspace under its own origin-local `pc-resume:` key. An applicable per-tab reload snapshot takes precedence, preserving that browser tab's workspace. When none exists, the host restores the newest remembered workspace. Closing a window still removes its reload snapshot, while the remembered workspace survives. A secondary instance must omit this option. Another host can omit the capability; Editor then retains its normal unsaved-window warning.

Registrations have separate random identities so an older page cannot overwrite another page's draft. A workspace timestamp advances when its captured state changes, rather than when an idle page flushes. Divergent copies remain retained; the host does not delete another live writer's record. These copies consume the browser's storage quota. If that quota is exhausted, durable acknowledgement fails and the normal close warning remains available. This facility requires the secure-context Web Crypto API, including localhost development.

A registration seals its own record when it leaves and can no longer flush. A replacement registration may retire only the sealed parent it actually continued, after successfully storing the complete replacement and verifying the parent's timestamp and full payload. Routine close and reopen therefore does not accumulate a copy on every visit. Active, changed or divergent records remain available. A non-BFCache page exit also seals its registrations; an omitted exit event merely retains an extra recovery copy.

The validator runs before a remembered workspace is registered. A failed durable write makes `flush()` return false even if the per-tab reload write succeeded. Editor therefore cannot claim a draft will survive window closure when only its reload copy was written. The retained original resource revisions still govern all later saves.

Editor and Docs also handle unchanged legacy drafts during migration. They compare the recovered raw source and encoding format with the current resource. Matching visible text alone cannot establish that the bytes are unchanged. A differing signature, byte order or separator leaves the draft protected. Legacy signature-bearing source can preserve an exact copy under the decoded-body convention without acquiring a writable baseline for the original file.

## Verification

The content-kit tests cover original baselines, matching and stale revisions, legacy drafts, unavailable resources, invalid payloads, registration ordering, failed writes and snapshot-key migration. The independent Diagrams artifact runs matching, stale and legacy recovery against a disposable host with synthetic files, real browser storage and actual source editing. It checks quota refusal and preservation of unsupported future snapshots without using the yavc server or guest VFS.
