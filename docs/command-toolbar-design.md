# Shared common-command toolbar

Paul authorised this batch on 5 November 2026 after the editing productivity release. Diagrams, Editor/Docs and Slides need a compact toolbar below the topbar whose contents the reader can change. The toolbar uses the current command tables, and the architectural principles remain in `C:\Users\paul\OneDrive\Documents\Architectural Principles.md`.

## Decisions

1. **The host owns the toolbar controller.** The optional `pudlHost.commandToolbar.attach(root, options)` capability receives an app key, label, default command-ID/separator array and the applet's command-table function. It returns `commands()` for the applet to include in that same table and `destroy()` for disposal. It renders inside the existing toolbar slot. Participating applets return no additional toolbar descriptor when this controller is present and retain their old descriptor as a fallback on other hosts. No PUDL files are patched.

2. **The existing command table remains authoritative.** Buttons carry `data-command`; PUDL supplies their glyphs, labels, menus, shortcuts, enabled state and pressed state. The controller reads the documented table fields to build its customization catalog, including nested command objects. The host extension `toolbarLabel`, a string or function on a command, can disambiguate its catalog label without changing its normal UI label. Diagrams uses it to distinguish Canvas and D2 commands with the same name. The controller registers no competing command scope. Saved commands that are unavailable in the current document remain in the preference and return when available. Unknown IDs are preserved but have no button and cannot invoke arbitrary code.

3. **Preferences belong to each app.** The host's `command-toolbars` configuration file stores one version-1 record per app, with `items`, `visible` and `inRibbon`. Editor and Docs use the same app key within a session. Deployed parent-domain cookies share that session; bare localhost runs intentionally keep host-only sessions, as the existing server contract requires. The default bar is visible in both menu and ribbon modes. The reader can hide the bar or have it give way to the ribbon. The toolbar controller ignores malformed fields, limits a bar to 60 entries and deduplicates command IDs. Loading never rewrites preferences. Other apps' settings remain intact.

4. **Customization edits a draft.** View offers Show the Toolbar and Customize Toolbar. The toolbar's final control also opens Customize Toolbar. Its shared PUDL dialog contains searchable available commands and an ordered chosen list, with Add, Remove, Move Up, Move Down and Add Separator actions. Restore Defaults edits the draft. Apply saves before replacing the running layout; Cancel and Escape discard an unapplied draft. Failed writes leave the draft open with an inline error. Keyboard users can operate the native lists and every action button.

5. **The common bar remains small by default.** Diagrams starts with Save, Undo/Redo, Drawing Tool, node/connection commands and zoom/fit. Drawing Tool is an ordinary command submenu of the existing shape toggles, and individual shape commands can also be added. Editor starts with Save, Undo/Redo, common formatting and insertion commands. Slides starts with Save, slide creation/layout, formatting and presentation commands. Slides has no published Undo/Redo commands, and its current text-history behavior needs separate work before those controls are added. Each bar also offers a View menu button. Menus retain the complete catalog.

6. **PUDL owns responsive behavior.** The shared bar uses labeled `.toolbar-group` elements and `data-toolbar-fold`. Labels remain while space permits; PUDL folds groups into glyphs and menus as needed and owns toolbar keyboard navigation. Separators start a group, whose caption comes from its first command so folded groups have distinguishable names. The controller does not implement another overflow algorithm or pressed/focus appearance. Preference changes rebuild the layout, while normal document edits let PUDL update existing controls.

7. **Instances share preferences and dispose independently.** Configuration notifications update other open instances of the same app without sharing document state or command handlers. A controller ignores late load/save responses after disposal, unsubscribes listeners and closes its own customization dialog. Closing one window leaves other windows' toolbars active. The Slides presenter can still hide its toolbar slot. A missing configuration service permits default commands but disables customization and preference changes with a reason.

8. **Command transfer uses aligned lists** (2026-11-05, Paul). Available Commands and Toolbar Commands share their top edge and height. Search Available Commands sits above both lists. The central `>` button adds the selected available command, and `<` removes the selected toolbar command; their accessible names and tooltips describe those actions. Move Up, Move Down and Add Separator remain below Toolbar Commands, with PUDL's arrow glyphs on the ordering buttons. Narrow dialogs retain horizontal transfer direction and let the ordering controls span the form. A wrapping line below each list shows its selected command's complete name, including format context, so clipped native option text remains identifiable. Native options expose the full accessible names; duplicate visual readouts do not announce the selection again.

9. **The controller comes in the content package** (2026-11-12, Paul; DESIGN.md, decision 133). A host other than yavc.app loads `support/command-toolbar.js` and `support/command-toolbar.css` from the package, with `support/yavc-util.js`, `support/dialogs.js` and PUDL's toolbar, command and dialog scripts, which the applets need already. It then offers the capability in a few lines:

    ```js
    pudlHost.commandToolbar = { attach: function (root, options) {
        return yavcCommandToolbar.attach(root, Object.assign({}, options, { config: pudlHost.config }));
    } };
    ```

    The controller asks three things of `config`. `load('command-toolbars', {})` resolves to an object with one record per app key (`editor`, `docs`, `slides`, `diagrams`), or to `{}` when nothing is saved. `set('command-toolbars', { <app>: record })` saves that app's record without disturbing the others, and resolves to nothing, or to a sentence when it could not save. `onChange('command-toolbars', fn)` is optional; it calls `fn` with the whole object when another window saves, and returns a function that stops it. A host with no `set` still gets the default bar, with Customize Toolbar unavailable and the reason given. The control at the end of the bar is a pencil, drawn as a glyph alone at every width and labelled Customize Toolbar. `scripts/test-portable-toolbar.cjs` runs this in the package's own lab host, at `workspace-lab/index.html?toolbar=1`.

## Acceptance

The combined browser fixture must cover all three applets, persistence across reload, Cancel, Reset/Apply, save failure, command state and dispatch, a drawing-tool submenu and individual shape toggles, ribbon visibility, narrow folding and keyboard access. It must also cover separate desktop windows, shared preferences without cross-window command dispatch, disposal, hostile preference input and the existing host fallback. Existing editor/diagram workflows must remain covered. Independent PUDL review and the repository gate run on the assembled candidate before a PR is offered for merge.
